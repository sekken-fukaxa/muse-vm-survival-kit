# 道具導入チェックリスト

## 導入前

- [ ] その道具は本当に要るか（既存の道具・連携で代替できないか）
- [ ] 置き場所は `~/workspace/tools/` か（apt の場合は `reinstall.sh` で再現できるか）
- [ ] ディスクとメモリの残量を確認したか（`df -h ~` / `free -g`）
- [ ] バージョンを固定するものはあるか（リリース番号、pip の `==` 指定）
- [ ] 取得経路は公式か（GitHub リリース、公式配布元、PyPI、npm）

## 導入中

- [ ] 単体バイナリは `tools/bin/` へ、Python 系は venv へ、npm 系は `tools/<name>/` にローカル導入
- [ ] 依存が衝突したら、既存 venv を汚さず専用 venv を切る
- [ ] モデル・辞書・フォント等のデータも `tools/` 配下に置く
- [ ] `bin/` へのリンクまたはラッパーを用意する（環境変数が必要な道具はラッパー側で吸収）

## 導入後（ここまでやって初めて「完了」）

- [ ] **実テスト**: 実際の仕事を 1 回やらせる（変換・生成・保存→復元などの往復）
- [ ] 出力の中身を検めた（エラーが出ない失敗を見逃さない）
- [ ] `reinstall.sh` に対応する節を追記し、節が冪等（再実行しても壊れない）か確認
- [ ] バージョン固定の理由など、後から要る事情をコメントに残した
- [ ] 覚えておくべき事実（癖・制約・置き場所）はメモリ／記録に残した

## VM 入替が起きたら

- [ ] まず `~/workspace/tools/` の無事を確認（たいてい無傷）
- [ ] apt ロックが空くのを待つ（ランタイムの自動復旧が先に走ることがある）
- [ ] `reinstall.sh` を実行し、最後のバージョン確認節が全部通るのを見る
- [ ] 通らない道具は、節単位で切り分けて原因を見る（一括で諦めない）
